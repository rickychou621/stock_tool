# 股票告警系統 — 總體規劃

## 1. 專案目標

打造一套針對台股的個人化告警系統:持續監控符合特定技術面條件的股票,透過 Telegram 推播提醒,並提供一個簡易網頁介面查看篩選結果、管理持股觀察清單。系統只做「觸價提醒」,不涉及自動下單。

## 2. 核心設計理念:條件庫 + 規則組合

系統不把「戰法」寫成寫死的整包邏輯,而是拆成兩層:

- **條件庫(Condition Library,程式碼層)**:每個技術判斷拆成最小顆粒、可參數化、彼此獨立的條件,例如「EMA黃金交叉(短週期、長週期、時框可調)」「價格站上布林中軌」「KD黃金交叉」「MACD DIF>0」「爆量倍數」等。
- **規則組合(Watch Rule,資料層)**:使用者在前端自由勾選條件,用 AND/OR 邏輯組合成一條「監控規則」,存成資料而非程式碼。新增戰法組合不需要改程式、不需要重新部署;只有要新增「從未寫過的全新指標」時才需要動到條件庫程式碼。

這個設計取代了「戰法一、二、三各自寫死一套邏輯」的做法,讓系統對未來新增戰法/組合保有高度擴充性。

## 3. 目前規劃的三套戰法(作為條件庫的起始內容)

| 戰法 | 核心邏輯 | 所需時框 | 更新頻率 |
|---|---|---|---|
| 戰法一:短分時多時框 | 2K/5K/15K/60K 的 EMA10/60 黃金交叉 + 左側爆量城牆K防守 + 大戶買力濾網(免費資料近似) | 分K(即時) | 即時盤中 |
| 戰法二:布林上軌區間 | 還原日K；20MA高於5個交易日前且收盤未跌破20MA，突破布林上軌仍符合 | 日K(還原股價) | 每日 |
| 戰法三:長波佈局 | 月K的 KD 黃金交叉 + DIF/MACD>0,搭配角度斜率與KD高檔鈍化判斷停利 | 月K | 每月/每日檢查 |

角度/斜率類的主觀判斷(如「均線角度」),統一用**區間高低點連線取斜率、以百分比/log價格標準化後取 arctan** 的方式量化,避免不同股價水位的股票角度不可比。

戰法二於2026-10-07確認：上軌只用來說明價格位置，不作為排除條件；收盤等於月線仍符合，低於月線當日即不符合，不等待連續兩日。月線上揚仍為必要條件，預設與5個交易日前比較，可由 `slope_lookback` 調整。回檔月線進場是另行觀察的買點，現有條件不產生買價或自動停損指令。

觀察清單會額外標示上軌壓力參考：收盤高於當日上軌為「突破上軌」；其餘當日最高價大於或等於當日上軌為「觸及上軌」。這是收盤後依完整日K計算的註記，不代表盤中即時觸發，也不影響戰法通過與否。掃描與通知的原因文字同樣保留此註記。

## 4. 資料源

| 用途 | 來源 | 費用 | 備註 |
|---|---|---|---|
| 日K、歷史股價 | FinMind (`TaiwanStockPrice`) | 免費,不需token | **已修正**:原規劃用 `TaiwanStockPriceAdj`(還原股價),但實測該dataset目前需要付費會員才能查詢(匿名/免費請求會被拒絕);改用未還原的原始股價 `TaiwanStockPrice`,實測確認免費可用 |
| 還原股價 | 自行計算(原始股價 + FinMind `TaiwanStockDividend` 股利事件,依TWSE除權息參考價公式反推) | 免費 | 已實作(`app/market_data/price_adjustment.py`),`stock_price_daily`的`adj_*`欄位存還原後的結果,圖表/指標一律讀這組欄位。目前只驗證過純現金股利的案例;若遇到有股票股利/減資的股票,換算單位需要額外核對 |
| 每日批次全市場資料(粗篩用) | FinMind / TWSE、TPEx OpenAPI | 免費 | 無訂閱數限制,可一次拉全市場 |
| 即時盤中 tick / K線 | 券商官方API(永豐 Shioaji / 富邦新一代API) | 開戶即免費 | 有同時訂閱數上限(如100檔),需搭配動態換股機制 |
| 籌碼濾網近似 | 三大法人買賣超、融資融券(FinMind/TWSE) | 免費 | 無法完全複製「大戶買賣力道」這類商業加工指標,僅作近似 |

籌碼K線、XQ全球贏家皆評估過:籌碼K線無官方API;XQ的量化功能(XS語法)是封閉生態,邏輯需寫在其軟體內部執行,無法讓外部系統呼叫其資料,兩者皆不適合作為本系統的資料串接來源。

## 5. 系統架構:兩階段篩選漏斗(含盤中動態換股)

```
1. 資料層
   ├─ 批次 EOD/月頻資料 (FinMind/TWSE OpenAPI) — 免費, 無訂閱限制
   └─ 即時盤中資料 (券商API) — 免費開戶, 有訂閱數上限

2. 篩選層 (兩階段漏斗，含盤中動態換股)
   ├─ 第一階段：粗篩 (每日或固定間隔跑一次，間隔/名單上限可外部設定)
   │    用免費批次資料掃全市場 → 依量增、法人買超、均線排列等條件
   │    產出候選名單 (數量壓在訂閱上限內，目前預設：5分鐘一次、上限10筆)
   │
   └─ 第二階段：即時細判 (只對候選名單 + 持股清單做)
        對候選名單做即時 tick/K線訂閱 → 跑戰法一類的即時規則判斷
        │
        └─ 盤中動態換股：
             用免訂閱的快照輪詢 API 定期重掃全市場排行
             → 候選股條件已失效就從訂閱池移除，挪出名額給新出現的強勢股
             → 持股清單(手動維護)獨立於候選池，固定監控、不受粗篩結果影響，
               規則判斷邏輯不因是否為持股而不同

3. 規則評估層
   ├─ 條件庫：所有技術判斷的最小單位實作
   ├─ 規則組合：使用者自由拼裝的 AND/OR 條件組合，存於 DB
   └─ 混合頻率規則：每日頻條件的計算結果需快取(當天有效)，
        供即時評估時直接取用做 AND/OR 運算，不必每次重算日頻邏輯

4. 推播層
   └─ Telegram bot：規則觸發時推播標準化格式的提醒(股票代號、觸發規則、觸發原因、參考價位)
```

## 6. 快取層設計(為未來 Redis 保留空間)

v1 不引入 Redis,快取邏輯(候選池/持股清單的即時查詢、每日條件結果暫存、告警防重複發送)先抽象成一個 `CacheService` 介面,以 backend process 內的記憶體結構實作。原因:目前 backend 僅單一 process 運行,不需要跨 process 共享狀態,MySQL 也足以應付現有資料量與頻率。未來若 backend 擴展為多 worker,或需要 WebSocket 多client即時推播(pub/sub),再替換此介面的實作對接 Redis,不需重新設計規則評估流程。

## 7. 技術棧總覽

| 部分 | 技術 |
|---|---|
| 後端 | Python + FastAPI,DDD-lite(feature-folder)架構 |
| 前端 | React + TypeScript + Vite |
| 資料庫 | MySQL + phpMyAdmin |

## 8. Docker Compose 服務規劃

| 服務 | 說明 |
|---|---|
| `frontend` | nginx:alpine,serve React build,內部 reverse proxy `/api/*` 到 backend,對外開 80 |
| `backend` | python:3-slim,FastAPI + APScheduler,另開一個 port 方便直接測試 API |
| `db` | MySQL 官方 image(非alpine,官方無此變體),儲存每日股價、規則、候選池、持股清單、告警紀錄 |
| `phpmyadmin` | 官方 image,提供熟悉的資料庫管理介面 |

## 9. 開發環境與資料夾結構

開發環境:WSL2 Ubuntu,專案根目錄 `~/dev/ricky/stock_tool/`

```
stock_tool/
├── backend/        # FastAPI 專案(見 backend.md)
├── frontend/        # React 專案(見 frontend.md)
├── config/          # docker-compose.yaml、Dockerfile、nginx.conf、.env(部署/環境層設定)
├── mysql/           # 初始化SQL script、volume mount 資料目錄
└── docs/            # 本規劃文件
```

語言工具鏈自身的設定檔(`pyproject.toml`、`package.json`、`tsconfig.json`、`vite.config.ts` 等)留在 backend/frontend 各自根目錄下,不搬進 config/,以維持工具與編輯器的預設行為。

## 10. 建議開發順序

1. **v1**:戰法二、三(每日頻率) + Telegram 推播,純批次資料,不碰即時訂閱與訂閱數限制問題
2. **v2**:戰法一的即時多時框判斷,先固定訂閱一份小名單測試邏輯
3. **v3**:加入兩階段粗篩機制 + 盤中動態換股,讓即時規則能覆蓋更大範圍的股票池
4. **持續擴充**:透過條件庫+規則組合機制,依需求新增技術條件與自訂監控規則,不需大幅調整核心架構

## 11. 尚待決策/後續事項

- 各條件的具體量化門檻(如角度斜率的臨界值、爆量倍數門檻)需要實際跑歷史資料回測調整
- 觸價提醒的觸發防重複規則細節(同一規則同一天只提醒一次?或允許重新觸發?)
- 券商API申請(永豐 Shioaji 或富邦新一代API)的開戶與簽署流程需另外處理
