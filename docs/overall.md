# 股票告警系統總覽

本文件以目前程式行為為準，涵蓋已完成的三個階段：觀察清單每日評估、歷史戰法回測、全市場掃描。系統提供收盤後技術條件篩選與 Telegram 通知，不自動下單。早期盤中即時訂閱、動態換股與券商 API 構想目前暫停，不能視為已實作功能。

## 操作流程與頁面

以「先檢查追蹤股票，再從掃描結果尋找新標的」為主要流程。

| 頁面 | 目前行為 |
|---|---|
| 觀察清單 `/`、`/watchlist` | 首頁；維護追蹤股票、族群、進場資料與筆記。進入頁面或新增股票不自動評估；按評估後先更新行情，再評估所選戰法並保存結果。通過、未通過、資料不足與過期結果分開顯示，有通過時集中呈現通過的戰法 |
| 全市場掃描 `/market-scan` | 上市普通股與 ETF 初始化、手動／自動掃描、進度、候選篩選及錯誤查詢；與觀察清單、舊候選池獨立 |
| 戰法回測 `/backtest` | 手動對目前觀察清單執行最近三年回測，查看整體／個股績效及交易明細 |
| 今日符合戰法 `/matches` | 依資料庫既有行情掃描可評估股票；只建立命中結果與告警紀錄，按通知按鈕才發送 Telegram |
| 候選池 `/candidates` | 保留既有粗篩功能與獨立導覽；不是階段三全市場掃描的前置篩選 |
| 查看個股 `/chart` | 股票名稱與族群、還原日 K、EMA／布林疊圖、KD／MACD 副圖與游標數值 |
| 規則管理 `/rules` | 管理規則與條件參數，不在此頁做個股評估；有告警歷史的規則刪除回傳 409 |
| 設定 `/settings` | 系統設定與資料操作入口 |

圖表的 KD／MACD 使用日 K；戰法三使用月 K，兩者不是同一時框的訊號。介面以操作用途區分按鈕配色，並呈現明確的評估狀態。

## 條件庫與戰法

條件以 `Condition` ABC、`@register_condition` 與 registry 實作；`WatchRule` 用 AND／OR 組合多個 `WatchRuleCondition`。手動評估、排程、回測及全市場掃描共用 `backend/app/rules/evaluation.py` 的 `RuleEvaluationService`，歷史行情經 `evaluate_bars()` 使用同一套邏輯。

| 條件／戰法 | 現行判斷 |
|---|---|
| EMA 交叉、爆量 | 依目前條件參數評估既有日 K；不代表已完成戰法一的即時多時框、大戶買力濾網 |
| 戰法二 `bollinger_mid_up` | 還原日 K 的 20 日均線高於 `slope_lookback` 個交易日前，且收盤大於或等於中軌；預設比較 5 個交易日前。突破上軌仍通過，中軌下彎或收盤跌破中軌則不通過 |
| 上軌註記 | 收盤高於上軌標「突破上軌」；其餘最高價觸及上軌標「觸及上軌」。僅供壓力參考，不影響通過，也不產生買價或停損指令 |
| 戰法三 | 月 K 的 KD 黃金交叉、MACD DIF 與訊號線均為正、MACD 柱狀體比上月增強，三條 AND。沒有另加角度、KD 高檔停利或自動賣出判斷 |

月 K 由截至評估日的日 K 聚合，當月為尚未結束月份的累積值。歷史不足會回報資料不足，不當作未通過或命中。條件輸出的數值指標可供全市場候選查詢，前端不另寫戰法判斷。

新增或修改 condition 時，Python registry 不會自動同步 `condition_catalog`；須一起維護 `mysql/init/002_seed.sql` 與既有資料庫。

## 三階段執行方式

| 階段 | 對象與觸發 | 結果與通知 |
|---|---|---|
| 一：觀察清單每日評估 | TWSE 交易日台北時間 18:00；設定可保存啟用狀態與戰法，預設啟用；最多 3 檔並行 | 更新行情、共用引擎評估，保存最新摘要及錯誤歷史；失敗保留舊有效結果並標過期。不發 Telegram、不補跑、不自動重試 |
| 二：歷史戰法回測 | 獨立頁面手動啟動；目前觀察清單、最近三年；一個回測任務、最多 3 檔並行 | 保存最近任務及每股票×戰法最新成功結果；無排程及 Telegram |
| 三：全市場掃描 | 上市普通股／ETF；獨立初始化、手動掃描、交易日 19:00 自動掃描；預設啟用且選取已啟用戰法 | 任務完成原子發佈候選；Telegram 只發一則批次完成狀態，不含逐股明細 |

交易日採 TWSE 實際成交日期，包含臨時休市。沒有執行中的工作接續或錯過排程補跑。後端重啟時將未完成任務標為中斷，保留已成功寫入的行情與已發佈結果。

### 階段一

排程設定與手動操作分開，使用者不必每次重選。沒有選戰法時仍同步一年行情。結果依行情版本與規則設定判斷是否過期；更新失敗不能假裝使用舊行情完成本次評估。手動單股評估多條戰法時只同步一次行情。

### 階段二

優先使用資料庫歷史資料，缺漏才同步，並取得指標暖機期間。每個歷史時點只讀當時已生效的行情、股利與價格事件，下一有效交易日開盤模擬成交；零價／零量不當作可成交日。同一股票×戰法同時最多一筆持倉。

績效包含勝率、平均／複利報酬、最大回撤、獲利因子與交易明細；未平倉不混入已實現績效。部分失敗保留舊結果但標過期，排除於本次整體績效。實際買賣規則與統計限制見階段二交付文件。

### 階段三

每次任務更新 TWSE ISIN 上市名單，含上市創新板普通股，排除上櫃、特別股、ETN、權證、TDR、REIT。名單來源異常或完整性檢查失敗沿用舊有效名單，無可用舊名單才失敗。這份名單不改使用者觀察清單。

初始化提供下載歷史行情、補齊歷史股利與補齊分割／減資，依所選條件的回看與暖機需求補缺，完成後都不自動掃描。日常掃描只更新基準日及前 5 個交易日的必要區間，不自動補更早歷史。有效日 K 最多可落後 5 個實際交易日，結果會標示較舊行情；條件歷史不足另列資料不足。

初始化、自動、手動掃描共用任務鎖，不排隊；與回測使用不同鎖，可並行。行情在 worker 啟動前按日期使用 MI_INDEX 批次寫入。預設 5 worker 各自 DB Session，只讀資料庫評估；TWT49U 先偵測除權息，僅缺少事件的標的使用 FinMind，每分鐘 4 次。所有 TWSE／ISIN 呼叫共用至少 3 秒間隔。初始化純行情節流約 40 分鐘，另加股利與運算時間。

全市場所有戰法只列入進場事件：今天符合且前一個有效交易日不符合。前日以同股票有效日 K 序列移除最後一筆後交由共用引擎評估；連日符合仍算成功評估，計入延續中，不產生候選或訊號歷史。前日資料不足列為歷史不足並記錄原因，不當作進場。觀察清單與回測判定不變。成交金額門檻僅用於頁面查詢篩選，不加入掃描判定。

候選在任務結束後一次 transaction 發佈，執行期間仍可看上次結果。成功評估不再符合者移除；失敗或歷史不足只保留既有列並標異常，不製造新命中。預設只查正常命中，支援名稱／代號、戰法、日期、價格、量、實際成交金額、數值指標、狀態的伺服端篩選、排序、分頁。行情落後但成功評估與評估失敗沿用舊結果是不同狀態。

前端執行中每 3 秒更新進度，完成刷新保留篩選、排序及頁碼。只保存最近一次掃描與初始化任務及其錯誤，沒有完整任務歷史、CSV 匯出或直接加入觀察清單按鈕。

## Telegram 通知

掃描結果通知與階段三完成通知是兩種流程。

| 來源 | 發送方式 |
|---|---|
| 今日符合戰法的通知按鈕 `POST /alerts/notify` | 接受既有告警 ID，只通知命中紀錄；每則最多 50 筆股票×戰法，依文字長度可能提早分段。包含股票代號、名稱、戰法、行情日期／參考價及已有上軌註記；詳細判斷理由保留在系統與告警紀錄 |
| 階段三掃描完成 | 自動發一則成功／部分失敗／失敗摘要與台北完成時間；不附逐股清單。未設定或發送失敗只記 task warning |
| 觀察清單每日評估與歷史回測 | 不發通知 |

例如 120 筆一般長度的命中會分成 50、50、20 筆三則。同股票通過不同戰法各計一筆。摘要不超過 Telegram 訊息長度限制；長文字提前分批，過長的單筆摘要截短，完整告警不截短。

告警依同日股票×戰法沿用既有紀錄；成功通知後保存 `is_notified`，重按略過。批次成功才將該則訊息對應的告警標為已通知；某批失敗不影響前面已成功的批次，可手動重試失敗項目。發送時按固定 ID 順序取得資料列鎖，避免重複點擊同時發送，相鄰批次間隔至少一秒。

Telegram 與 MySQL 沒有共同交易：若 Telegram 已收到但回應逾時，或發送成功後 DB 提交失敗，重試仍可能重複，不能保證外部投遞恰好一次。

| 部分 | 現況 |
|---|---|
| 後端 | Python 3.12、FastAPI、SQLAlchemy，DDD-lite／feature-folder |
| 前端 | React、TypeScript、Vite，feature-folder |

| 外部來源 | TWSE 全市場日 K、除權息偵測、上市名單及交易日；FinMind 觀察清單／回測日 K 與股利細節 |
| 還原股價 | `market_data/price_adjustment.py` 共用自行還原算法，寫入 `stock_price_daily.adj_*`；不依賴付費 `TaiwanStockPriceAdj` |

API 回傳 camelCase，Python 內部 snake_case。規則、條件、資料來源、行情、告警、觀察清單、排程、回測、全市場掃描各自維持 feature 邊界，共用行情與評估模組。

`Trading_money` 保存實際成交金額，來源沒有值時保持 null，不用價格乘量推估。行情有效性、來源覆蓋與資料版本用來區分本次有效評估、歷史不足及舊結果。

## 開發與部署

專案位於 `~/dev/ricky/stock_tool/`。Compose 在 `config/`，開發使用 `docker-compose.yaml` 加 `docker-compose.dev.yaml`。前端開發服務為 5173，透過 `/api` 代理後端；正式前端由 Nginx 提供靜態檔與 API 代理。

```text
stock_tool/
├── backend/app/       # 功能模組與共用核心
├── backend/tests/     # 單元、隔離整合與手動 MySQL 驗證
├── frontend/src/      # React 頁面、元件與功能模組
├── config/            # Compose、Dockerfile、環境範本
├── mysql/init/        # 初始化與增量 migration
└── docs/plan/         # 各階段需求、交付與驗證紀錄
```

部署須套用相應 migration；既有資料庫不會因重建容器自動執行新增的 init SQL。006、007、008 分別對應三階段資料結構，操作見根目錄 README。MySQL CLI 必須使用 `--default-character-set=utf8mb4`，避免中文寫入亂碼。

後端以 Ruff、pytest 單元／整合測試驗證，外部來源與 Telegram 在自動化測試中 mock。前端以 TypeScript、ESLint、build 與瀏覽器操作驗證，不新增 Vitest。第三階段節流目前僅適用單 backend process／replica，多副本需先調整排程及分散式節流。

## 已知限制與暫停項目

- 不串接券商 API、不提供盤中即時 tick／多時框訂閱，不做自動下單或身分驗證。
- 共用還原算法已納入分割／反分割與減資價格事件，完整性取決於來源同步是否成功。
- 已確認來源無行情的歷史區間不反覆下載；來源事後補資料目前無強制刷新入口，維護方式見階段三交付文件。
- 階段三共享 FinMind 額度不包含階段一、二或同 IP 其他工具；來源配額失敗記錄錯誤，不自動重試。
- 全市場批次手動掃描驗證結果見階段四 A 交付；完整三年初始化及真實 19:00 排程尚未驗證。自動排程依使用者要求保持關閉。

`market_scan/batch_data.py` 負責下載與 coverage；`MarketDataService.import_market_day()` 共用既有還原算法，單日行情、還原價與 coverage 同一交易提交。來源失敗無重試、無逐檔行情備援；股利不一致列逐股警告，仍評估。`FINMIND_API_TOKEN` 已接入 Bearer header，`TWSE_MIN_REQUEST_INTERVAL_SECONDS` 預設 3。009 migration 不改既有排程設定。

全市場掃描若股利核對未涵蓋所選戰法的回看期，該標的列為 `insufficient_history`，原因顯示「還原資料未完整」，不當成正常命中。初始化的成功數代表行情資料可用，不代表戰法命中；股利或來源錯誤會列警告及 partial_completed。既有事件會重用，舊資料沒有核對紀錄時仍需手動補齊歷史股利。此次沒有自動重啟已中斷初始化。

## 階段四 C：回測成本與基準

共用 `app/trading_costs.py` 計算比例成本。`backtest/costs_benchmark.py` 在原模擬產出後附加毛／淨報酬與 0050 比較，沒有改變策略判斷、成交時間或還原算法。`returnRate`、`unrealizedReturn` 與 `metrics` 在 schemaVersion=2 結果代表淨值，另提供 grossReturnRate、grossUnrealizedReturn、grossMetrics。

回測接受時保存 costSnapshot；準備交易日期後整批下載／讀取一次 0050，使用同一結束日還原基準。個股種類取 market_scan_instruments，未知採普通股並記錄警告。逐筆交易基準為同日開盤到開盤；個股與戰法整體的買進持有基準為實際期間首日開盤至末日收盤。基準缺資料不影響策略回測，回傳 null 與原因。平均超額只計入有可比較基準的已平倉交易。

API 路徑維持 `/backtests`、`/backtests/latest`、`/backtests/results/{id}`。新增 costSnapshot、grossMetrics、averageExcessReturn、benchmarkBuyHoldReturn、needsRerun 等欄位。舊結果不冒充淨值，顯示需重新回測並排除於本次淨績效彙總。前端並列毛／淨績效、成本設定與 0050；不增加前端自動化測試。

011 migration 新增 task.context_json 保存成本及 0050 價格快照，結果仍保存於既有 JSON，沒有新增績效追蹤表。此次沒有啟動回測或任何初始化，排程保持原設定。
## 階段四 B：訊號歷史與後續績效

掃描的正常進場事件在原子發佈交易內寫入 `market_scan_signal_history`，同日同股票同戰法保留首次快照；非正常結果不記錄為新訊號。發佈後使用 `signal_tracking.backfill()` 分批讀取 DB 日曆、行情與 0050，回填到期且未完成的觀察期，不呼叫外部 API。回填失敗只新增警告，不回滾已發佈候選。

`GET /market-scan/signal-performance` 提供戰法 × 觀察期統計，`GET /market-scan/signals` 提供明細。兩者支援 ruleId、from、to、kind、minTurnover、excludeOlderQuote；明細另有 ticker、signalDate、page、pageSize，預設 50、上限 200。

前端位於全市場掃描頁，顯示部署起日、淨績效、0050 超額與最大不利幅度。樣本少於 30 標示不足，未到期或資料缺漏不填 0。觀察期預設 1／5／10／20 交易日；觀察期 N 使用進場日之後第 N 個市場交易日收盤，觀察期 1 為進場隔一個交易日收盤。成本快照與部署日期持久化，migration 與操作說明見 README。

全市場摘要 `GET /market-scan/summary` 的 `continuing` 為本次延續中的股票 × 戰法總筆數，保存在發佈 metadata；舊發佈資料預設回傳 0。頁面顯示「延續中 N 筆（未列入候選）」，Telegram 完成通知格式不變。既有訊號歷史保留，由使用者另行清理，程式不刪除資料。

### 分割與減資價格事件

共用還原算法同時讀取股利與 stock_price_events。價格事件包含 split、reverse_split、par_value_change、capital_reduction。係數由來源參考價除以事件前收盤價取得，事件當日不套用自身係數，成交量不變；同日股利與價格事件各自累乘。

所有價格事件經 sync_market_price_events 同步，固定查詢 2011-01-01 至台北當天：FinMind TaiwanStockSplitPrice 不帶 data_id、TWSE TWTAUU 與 TPEx revivt 各全市場查一次。TPEx 參數使用西元 YYYY/MM/DD，回傳日期使用民國無斜線格式；兩個交易所共用 twse_client 節流器。FinMind 沿用批次任務的請求節流 callback。

18:00 觀察清單整批任務開始時同步；手動回測在確認交易日期後、0050 與股票準備前同步；全市場掃描及初始化 price_events/dividends mode 同樣呼叫此入口。行情／股利仍沿用原本近 6 個交易日或 required_days 範圍，價格事件不受該範圍限制。逐檔行情與 prepare_data 不查價格事件來源，只讀 DB。

stock_price_event_sync 的 id=1 紀錄台北 synced_on 與 complete。同步互斥鎖涵蓋檢查、抓取與寫入；MySQL 使用 connection advisory lock，避免不同任務／程序重複請求。當天 complete=true 時全部來源跳過，正常成功情況下價格事件的 FinMind 每天最多 1 次。任一來源或寫入失敗保留 complete=false，本次不重試，下次呼叫可重試；失敗日不承諾嚴格每日上限。回測 errors、觀察清單錯誤紀錄、掃描 warnings 均可見失敗，訊息不含 token；本次不寫 DividendCoverage。

同步先確保 0050 主檔存在，其他事件只保存 stocks 中已存在的代號。三來源均成功後才同交易匯入事件並標記完成；事件新增或價格修正才重算歷史還原價、增加資料版本並標記回測 stale。0050 變動會標記全部既有回測過期；已完成訊號追蹤結果仍不重算。
