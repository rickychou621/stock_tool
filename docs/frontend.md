# 前端規劃(React)

> 本文件聚焦前端實作細節,系統整體背景請參考 [overall.md](./overall.md)。此文件之後會針對開發過程持續調整。

## 1. 技術棧

- **框架**:React + TypeScript(一律使用 TypeScript,不使用純 JS,提升日後閱讀/維護時的可尋性)
- **建置工具**:Vite
- **資料同步**:TanStack Query(處理與後端API的資料抓取、快取、重新整理),不使用 Redux(目前規模不需要)
- **程式碼品質**:ESLint(`typescript-eslint` + `eslint-plugin-react-hooks`)+ Prettier
- **測試**(優先度低於後端):Vitest + React Testing Library
- **容器**:`nginx:alpine`,serve 建置後的靜態檔案,並將 `/api/*` reverse proxy 到 backend 容器

## 2. 架構風格:Feature-folder

與後端一致,採用依業務功能分資料夾,而非依元件抽象層級(不採 atomic design 的 atoms/molecules/organisms 分法),讓同一功能的 component、hook、型別集中好找。

## 3. 資料夾結構

```
frontend/
├── src/
│   ├── features/
│   │   ├── screening/        # 候選池顯示
│   │   │   ├── components/
│   │   │   ├── hooks/
│   │   │   └── types.ts
│   │   ├── watchlist/        # 持股清單顯示與手動新增/移除表單
│   │   ├── rules/            # 規則組合管理介面(勾選條件、設定AND/OR、CRUD)
│   │   ├── alerts/           # 今日符合戰法清單 + 告警歷史查詢
│   │   ├── chart/            # 個股查詢頁(走勢圖+技術指標+該股觸發紀錄)
│   │   └── settings/         # 系統設定(候選池更新頻率/上限、Telegram等,對應config/backend.env的可調參數)
│   ├── components/           # 跨feature共用元件(如版面、表格、按鈕等基礎元件)
│   ├── api/                  # 呼叫後端API的client(依feature拆分或共用一個base client)
│   ├── App.tsx
│   └── main.tsx
├── package.json
├── vite.config.ts
└── tsconfig.json
```

## 4. 主要頁面/功能規劃(待細化)

確定要做的五個頁面:

| 頁面 | 功能 | 優先度 |
|---|---|---|
| 今日符合戰法清單 | 顯示「今天」觸發了哪些規則的股票(代號、觸發規則、觸發時間、觸發價位),與「目前候選池」分開呈現(候選池=還在盯盤、尚未觸發規則;本清單=規則已成立) | 高 |
| 觀察清單 | 手動新增/移除持股股票代號,編輯進場價/進場日/備註 | 高 |
| 個股查詢頁 | 搜尋單一股票,查看還原日K/月K走勢圖、目前技術指標數值(EMA/布林/KD/MACD)、該股票過去的觸發紀錄 | 高 |
| 規則管理 | 從條件庫勾選條件、設定參數與AND/OR邏輯,組成自訂監控規則,啟用/停用規則 — 沒有這頁就無法定義任何戰法 | 高 |
| 系統設定 | 調整候選池更新頻率/上限、Telegram設定等,改了直接存後端,不用重新部署容器 | 低,v1可先用`config/backend.env`調整,之後有空再補UI |

告警歷史(查詢過去所有時間範圍的觸發紀錄,不限今天)歸在同一個 `alerts` feature 底下,與「今日符合戰法清單」共用資料來源,差別只在預設篩選範圍。

## 5. 與後端溝通

- 瀏覽器只會呼叫同源的 `/api/*`,由 frontend 容器內的 nginx reverse proxy 轉發到 backend 容器,避免跨域(CORS)問題
- 資料抓取一律透過 TanStack Query 管理,元件不直接處理 fetch 邏輯

## 6. 程式碼規範

- Component 一律使用 functional component + hooks,不使用 class component
- 檔名/元件名稱使用 `PascalCase`,一個檔案盡量對應一個 component
- 一般函式/變數使用 `camelCase`
- 型別定義盡量明確,避免使用 `any`

## 7. 待補充項目

- 各頁面的詳細UI/UX規劃與線框
- 規則組合介面的互動設計(如何呈現條件庫清單、參數輸入表單)
- 是否需要即時更新機制(WebSocket)或先以輪詢(polling)方式呈現最新資料

## 操作流程

觀察清單是首頁。進入頁面與新增股票不自動評估。選定戰法後，可逐檔評估或評估全部觀察股票。按下後依序顯示更新行情、評估與結果；結果區分符合、不符合、資料不足及失敗，並顯示行情日期與評估時間。結果儲存於資料庫，重新整理或重開瀏覽器仍可查看；行情更新或戰法條件變更後會標示需重新評估。

今日符合戰法清單的「立即掃描」使用已儲存行情，不同步行情、不發 Telegram。結果區分本次符合與今日歷史紀錄。「通知 Telegram」只處理本次符合項目，同股票同戰法當天已通知則略過，失敗項目可重試。掃描結果與候選池均可進入個股圖表或加入觀察清單。

候選池與今日符合戰法清單維持獨立頁面。規則管理僅處理規則設定。個股圖表的 KD／MACD 明示為日K口徑，戰法三仍用月K評估。

## 介面與操作層級

桌面採側欄導覽，手機改為可橫向捲動的導覽列。各頁統一標題、用途說明及卡片層級，表格在窄螢幕內獨立捲動。介面隨系統切換明暗模式。

按鈕依用途區分：深青色執行主要操作，淡青色加入觀察，紫色發送 Telegram，灰色執行單筆輔助操作，紅色移除或刪除。所有操作仍保留文字標籤、鍵盤焦點與停用狀態，不單靠顏色辨識。

觀察清單摘要顯示追蹤數量、選定戰法皆完成判斷的數量及至少通過一條的股票數量。日期、時間與判斷依據收進展開區。掃描結果另顯示本次檢查股票數、戰法數與符合股票數。

## 多戰法與清單管理

戰法可複選，預設選取已啟用戰法；手動仍可選擇掃描已停用的戰法。每檔股票依所選戰法需要的最長歷史範圍更新一次行情，再共用 RuleEvaluationService 逐條評估。評估全部按鈕處理整份觀察清單，不受結果或族群篩選影響。

結果可篩選全部、至少通過一條、全部未通過、資料不足、失敗、尚未完成、需重新評估。至少通過一條時，仍顯示其餘未評估或待確認條數；全部未通過必須所選戰法皆有有效判斷。任何所選紀錄過期時，股票先歸入需重新評估。可依族群篩選並選擇通過優先或代號排序。

編輯可更新進場價、日期、筆記與族群。族群是使用者的觀察分類，最初沿用指定的六組名單，不代表官方產業分類；股票主檔的族群也顯示在個股查詢頁。未指定者顯示未分類。
