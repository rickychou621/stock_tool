# Codex 執行任務：stock_tool 階段一

請在目前 `stock_tool` 專案**實際完成程式修改與測試**，不是只提供建議。本次僅實作「階段一：觀察清單每日自動行情更新與戰法評估」。

## 0. 開始前

1. 檢查目前 Git 狀態、專案架構及現有功能；保留所有未提交修改，不得覆蓋或還原。
2. 優先沿用既有 `MarketDataService.sync_daily_prices()`、`RuleEvaluationService`、觀察清單、戰法設定、Scheduler 骨架及 Migration 機制。
3. 技術環境：FastAPI / Python、React、MySQL、Docker Compose、FinMind。
4. 先簡述修改計畫及主要檔案，再開始實作；若遇到影響架構的重大歧義，先詢問。

## 1. 每日排程

- 時區：`Asia/Taipei`；**僅台灣證交所交易日 18:00** 執行，週末、假日及特殊休市日略過。請使用可維護的交易日判斷方式，不要只排除週末。
- 每個交易日最多自動執行一次；後端未啟動而錯過時間，不補跑；失敗不自動重試。
- 每次執行開始時，從 DB 取得當下觀察清單與已儲存設定，僅處理清單中的股票。
- 固定 **3 檔股票並行**，每個 Worker 使用獨立 SQLAlchemy Session；單檔失敗不阻塞其他股票。
- 沿用並實際註冊現有 Scheduler，避免同一排程重複觸發；不另做 FinMind 全域 API 限速器。

## 2. 行情同步與驗證

- 沿用 FinMind 現有同步流程：日K OHLCV、股利、還原股價；不新增增量同步。
- 同步足以支援所選戰法的完整歷史區間；多戰法取最長需求。
- **未選任何戰法**時，仍同步最近 **1 年**的基本行情及相關股利資料，但不執行戰法評估。
- 驗證最新日K日期等於本次交易日、OHLC 為有效正數且高低價關係正確、成交量非負（允許 0）、各戰法所需歷史資料足夠。
- 行情無效或歷史不足時，不以不可靠結果覆寫既有有效評估；保留原結果並可辨識其已過期，記錄原因後繼續下一檔。資料不足應清楚標記，不誤判為戰法不符合。

## 3. 戰法評估

- 直接重用現有 `RuleEvaluationService`，不要重寫戰法邏輯。
- 預設選擇所有**已啟用**戰法；允許取消部分或全部。
- 只執行選取且目前可用的戰法；未選取的戰法結果維持不變。
- 對尚未完成或無法執行的戰法，依現有程式能力明確處理，不得假裝評估成功。

## 4. 觀察清單前端

在現有觀察清單頁面上方新增：
- 自動排程啟用／停用（預設啟用）。
- 戰法勾選及「儲存設定」按鈕。
- 最近一次排程的執行時間、狀態、成功數、失敗數、錯誤資訊。

設定只在按下「儲存設定」且 API 成功後寫入 DB，**下次 18:00** 生效；儲存失敗時顯示錯誤並保留未儲存的畫面選擇。設定在後端重啟後仍保留。頁面資料僅需重新整理後更新，不實作輪詢或 WebSocket。既有手動評估功能維持正常。

## 5. 資料庫與記錄

使用現有 Migration 機制建立必要資料結構：
- **排程設定**：啟用狀態與所選戰法。
- **最新執行摘要**：僅保留可覆寫的最新一次執行資訊，重啟後仍可查詢，不累積成功執行歷史。
- **錯誤歷史**：永久保存股票代號（若適用）、時間、原因及可辨識的執行批次；整批排程失敗也需記錄。

歷史錯誤不得影響最新一次執行狀態；非交易日不執行、不新增執行紀錄。

## 6. 不做的功能

- Telegram 自動通知、全市場掃描、歷史訊號狀態追蹤。
- 額外 FinMind 全域限速器、自動重試、失敗股票補跑介面、錯過排程補跑。
- 即時前端推播、手動與排程同時執行的額外衝突協調。
- 階段二、階段三任何功能。

## 7. 驗收與交付

請補上測試並執行專案現有測試、Lint、Build（以專案工具為準），至少覆蓋：
- 交易日執行、非交易日略過、停用不執行、錯過時間不補跑、每日最多一次。
- 並行上限 3、單檔失敗隔離、API 限流時記錄錯誤且不重試。
- 無效行情／資料不足不覆蓋有效評估，未選戰法只同步行情。
- 設定儲存／失敗處理／重啟保留、最新摘要與歷史錯誤正確。
- 現有手動評估功能正常。

最後回報：完成項目、主要修改檔案、Migration、測試結果、未完成事項，以及 Docker Compose 啟動／驗證指令。
