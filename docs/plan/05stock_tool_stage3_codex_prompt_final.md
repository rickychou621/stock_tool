- 沿用 FastAPI / Python、React / TypeScript、MySQL、Docker Compose、FinMind、現有排程與 SQLAlchemy Session 模式。
- 使用 `MarketDataService` 共用日K／股利／還原股價資料，沿用 `RuleEvaluationService` 評估戰法及原因；前端只展示，不重新計算指標。

- 這不是自動交易系統，不新增券商下單或交易建議引擎。

## 3. 上市標的名單

- 僅臺灣證交所（TWSE）**上市普通股及上市 ETF**；排除 TPEx 上櫃、權證、ETN、特別股及其他不在上述兩類的標的。市場與種類欄位設計應可擴充。
- 每日 19:00 自動掃描前先更新官方／可信的上市名單：新增標的 upsert，已下市／終止上市標記 inactive，不刪歷史行情。
- 更新失敗時退回 MySQL 最近成功的有效名單，記錄及顯示警告；若無可用名單，掃描失敗。
- 避免將名單暫時取得不完整誤判成全數下市；驗證來源完整性再套用停用更新。
- 前端及任務統計要分清楚「應掃描標的總數」與「成功評估標的數」。

## 4. 行情初始化與增量同步

- 在「全市場掃描」頁新增**獨立的「初始化歷史行情」按鈕**，後端背景任務，不是掃描的隱含前置步驟。
- 初始化所需區間依**目前啟用／選用戰法中最長 lookback，加足夠 warm-up** 動態計算；不得硬編固定 3 年或 5 年。戰法新增／需求延長後可再次初始化。
- 每次初始化只補齊缺少或不完整的資料，避免重抓已完整區間；共用現有行情同步、股利及還原價計算。
- 初始化不限使用者重跑次數；同時間只能有一個階段三任務（初始化或掃描）。無取消、無中斷後續跑。
- 全部成功 => `completed`；部分成功 => `partial_completed`；全部失敗 => `failed`。記錄成功／失敗／不足數量、逐股錯誤及起訖時間。
- 後端重啟時未結束任務標記 `interrupted`，不自動恢復。關閉頁面不影響後端工作。
- 初始化完成**不自動掃描**；使用者手動掃描或等待下一次 19:00。
- 即使初始化未全部完成，掃描仍可對歷史足夠的標的執行；不足者跳過並記錄原因。
- 每日增量更新只補必要行情；FinMind 請求失敗不自動重試，下次任務再試。

## 5. FinMind 配額與資料安全

- `MARKET_SCAN_WORKERS` 預設 `5`，由環境變數調整，校驗為正整數；每個 worker 使用獨立 SQLAlchemy Session，避免跨執行緒共用 Session。
- `FINMIND_SCAN_REQUESTS_PER_MINUTE` 為全階段三工作者**共享**的速率限制，預設採保守值並寫入 `.env.example` 與文件。所有階段三對 FinMind 的呼叫（初始化／掃描增量）都受限制，不能每 worker 各有一份額度。
- 等待取得節流許可後再送請求；避免併發衝撞配額，無 API 失敗重試。
- 多進程／多副本部署時必須說明並實作有效的共享限制策略，或明確限制單一 scheduler／worker 實例以避免超額。
- API 失敗、資料不完整及異常要逐股隔離，不能把舊正常資料覆寫成無效值。

## 6. 自動排程與手動掃描

- 自動掃描：**19:00 Asia/Taipei**，僅 TWSE 實際交易日（含特殊休市判定）；預設啟用，開關持久化 MySQL；不補跑、不重試漏掉的任務。
- 手動掃描：頁面按鈕啟動**全市場**，交易日與非交易日皆可，不提供指定個股掃描。
- 自動掃描戰法選擇：預設全部啟用戰法，可勾選保存至 DB；手動預設讀取自動設定，但手動臨時改選**不寫回**。
- 自動戰法允許儲存空集合：19:00 記錄 `skipped` 與「未選擇戰法」，不修改候選清單；手動沒有任何戰法時禁用啟動。
- 自動開關關閉後不終止已啟動工作；手動仍可使用。
- 單一階段三任務同時執行；自動與手動、初始化互斥，衝突時回傳明確 409／等價錯誤，不建立佇列。
- 後端背景執行，前端每 **3 秒**輪詢任務狀態；重啟標記中斷不續跑；不提供取消功能。
- 前端與後端均防止重複啟動，後端應以可靠原子鎖／DB 狀態機防止競態，不僅靠前端禁用。

## 7. 資料有效性與戰法評估

- 依既有階段一驗證邏輯：OHLC 必須為有限正數且符合 high >= max(open,close)、low <= min(open,close)、high >= low 等關係；成交量不得為負，零量不直接視為資料損毀；交易日、資料完整性及戰法 lookback 必須有效。
- 可以使用最近有效行情，但相對掃描基準交易日最多落後 **5 個 TWSE 交易日**；超過跳過並記錄原因；候選列顯示實際行情日期及過期提示。
- 請區分：① **有效但非最新日K**（落後 <=5 交易日，若本次成功評估仍可列為正常命中，並加「行情較舊」提示）；② **上次掃描遺留的舊候選**（本次未成功評估，列為異常／過期，不可列入正常命中）。
- 歷史不足：跳過該股票／戰法並記錄原因；**掃描期間不臨時額外補抓歷史**，由初始化任務處理。若同股其他戰法歷史足夠，仍可評估可用戰法。
- 使用既有 `RuleEvaluationService` 的結果及理由（如 MA、KD、MACD），不在前端推算，不硬編僅支援特定戰法。
- **不預先以成交量、成交金額或均線粗篩排除股票**；候選流動性條件只屬查詢篩選。

## 8. 候選清單的資料模型與原子發佈（重要）

- 每筆候選以「**股票 × 符合戰法**」為單位；同一股票可因多個戰法符合而有多列。
- 自動與手動掃描共用**同一份最新候選清單**；手動掃描完成後依本次手動戰法集合取代候選資料，下一次自動完成後再以自動集合取代。
- 執行中前端仍讀取**上一批已發佈**結果；掃描完成後以單次交易或等效一致性策略**原子發佈**，避免半更新列表。
- **成功評估標的**：刪除其舊候選列，僅寫入本次所選戰法中成功命中的列；未命中及未選戰法舊列要移除。
- **失敗／資料不足標的**：保留原候選列，但標記 `stale`／`insufficient_history` 等狀態及失敗原因；不能誤當本次正常結果。若部分戰法成功、部分戰法歷史不足，按股票×戰法粒度正確隔離狀態。
- 沒有歷史候選的失敗標的可只記錄任務逐股錯誤／不足狀態，不必製造假的命中候選。
- 只保留最新候選與最近一次掃描任務；不保存逐次完整候選快照或任務歷史。最近一次初始化任務紀錄獨立保存。
- 每次發佈需保存批次 metadata：`source=automatic|manual`、完成時間、實際戰法 IDs/名稱快照、成功／失敗／不足數、正常命中列數、掃描基準日及警告。
- 掃描尚未完成或被中斷時，**不得發佈半成品**；既有候選清單保持可讀。
- 設計交易及索引以支持 `stock_id, rule_id, status, batch_id, price_date, volume, turnover` 等查詢；避免 MySQL 大交易鎖住長時間網路請求，計算在發佈交易外完成。

請實作或整合等價接口，提供一致的 request/response schema、錯誤碼與 OpenAPI：

| 用途 | 建議方法／路徑 | 重點 |

- 摘要至少包含成功評估**不同標的數**／預期掃描標的總數、歷史不足數、失敗數、命中列數；分開顯示正常與異常數，不將多戰法列數當成成功股票數。
- 逐股錯誤有可供前端檢視的摘要／查詢方式，避免無上限直接回傳所有錯誤。

## 12. DB、任務生命週期與併發

- 按現有 migration 工具新增所需資料表／欄位（建議涵蓋市場名單、掃描設定、最新掃描任務、最新初始化任務、候選結果、逐股錯誤及批次 metadata；若已有可用表則延伸而非重複建立）。
