# 股票告警系統

FastAPI / React / MySQL 的台股追蹤工具。提供觀察清單評估、歷史回測及上市普通股／ETF 全市場掃描；全市場行情按日期使用證交所 MI_INDEX；觀察清單、回測與股利細節維持 FinMind。

## 啟動

開發模式使用 `config/` 下兩份 Compose 檔案。先依各 `*.env.example` 建立對應 `.env`，既有設定檔請保留。

```sh
cd config
docker compose -f docker-compose.yaml -f docker-compose.dev.yaml up -d --build
```

前端為 `http://localhost:5173`；API 一律透過 `/api` 代理。正式 Compose 使用 port 80。

新 MySQL volume 會執行 `mysql/init/`。既有 DB 不會自動執行新增 SQL；升級第三階段前，先確認 `006_watchlist_schedule.sql`、`007_backtest.sql` 已套用，再執行：

```sh
cd config
docker compose -f docker-compose.yaml -f docker-compose.dev.yaml exec -T db \
  sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql --default-character-set=utf8mb4 -uroot "$MYSQL_DATABASE"' \
  < ../mysql/init/008_market_scan.sql
docker compose -f docker-compose.yaml -f docker-compose.dev.yaml up -d --build backend
```

`008` 可重複執行，新增第三階段資料表及可空的 `stock_price_daily.turnover`，保留原行情、回測與觀察清單。不要刪除 MySQL volume。

## 設定

`config/backend.env.example` 列出設定範本。DB 連線依本機環境填入；Telegram 完成通知需要 `TELEGRAM_BOT_TOKEN` 與 `TELEGRAM_CHAT_ID`。

| 變數 | 預設 | 用途 |
|---|---|---|
| `MARKET_SCAN_WORKERS` | `5` | 第三階段並行標的，正整數，最大 32 |
| `FINMIND_SCAN_REQUESTS_PER_MINUTE` | `4` | 所有第三階段 worker 共用，每次請求至少間隔 15 秒 |
| `TWSE_MIN_REQUEST_INTERVAL_SECONDS` | `3` | 所有 TWSE／ISIN 呼叫共用間隔秒數，須大於零 |
| `FINMIND_API_TOKEN` | 空 | FinMind Bearer token；不記錄於錯誤訊息 |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | 空 | 缺少時記錄通知警告，不阻止掃描 |
| `DB_HOST/PORT/NAME/USER/PASSWORD` | 見範本 | MySQL 連線 |

`FINMIND_API_TOKEN` 非空時使用 Authorization Bearer header，空值維持匿名。全市場使用 FinMind 查詢分割事件，並只對缺少的除權息事件逐檔查詢 FinMind，預設每分鐘 4 次；有 token 可依方案自行調高，不會自動提高額度。此額度不涵蓋階段一、二或同 IP 其他程式。

後端僅支援 **1 個 Uvicorn process、1 個 backend replica**，Compose 與 Dockerfile 已明示。節流在同一 process 共用；跨請求互斥另有 MySQL named lock。不要以多副本擴充目前排程服務。

## 操作

1. 在「全市場掃描」設定 19:00 的自動戰法與啟用開關，按儲存。預設啟用且使用所有已啟用戰法；空集合會略過。
2. 選擇本次戰法，先按「下載歷史行情」，再自行按「補齊歷史股利」。前者只補日 K，不查股利；後者彙整各月缺少的股利事件後，每檔一次查所需期間，並補分割／減資，不下載日 K。已有股利者可按「補齊分割／減資」，只補價格事件並重算還原價。三種操作都不會自動接著掃描。
3. 按「開始全市場掃描」，或等待交易日 19:00。手動戰法不改動自動設定；關閉頁面後工作繼續。
4. 候選預設顯示正常命中；可查過期／歷史不足，並使用伺服端篩選與每頁 50 列分頁。重新整理只查 DB。

全市場日常掃描最多補近 6 個交易日，每日一次 MI_INDEX，完整日期會略過；先完成下載，再由 worker 讀 DB 評估。初始化三年約 750 個交易日，純行情節流約 40 分鐘，另加股利補齊、來源與運算時間。初始化期間 19:00 掃描若衝突會略過，不排隊。缺歷史仍可掃描資料足夠的戰法。

觀察清單排程維持 18:00；全市場排程為 19:00，時區皆為 Asia/Taipei。依證交所實際交易日執行，不補跑；重啟只把未完成任務標成中斷。

完整實作、API、測試與限制見 [階段三交付文件](docs/plan/06stock_tool_stage3_delivery.md)。

## 階段四 A 升級

既有資料庫依序套用 `mysql/init/009_stage4.sql` 與 `010_dividend_coverage.sql`，方法同上方 008 指令，再重建 backend。009 新增日期 coverage 與行情日期索引，010 新增已核對股利的期間；皆可重複執行，不修改排程開關。使用者目前的全市場自動排程保持關閉。

階段四已完成 A 批次行情與 C 回測成本／0050 基準；B 候選績效追蹤已完成程式與本機部署，驗證見交付文件末節。來源失敗不重試，也不改走逐檔 FinMind 行情；沿用最多落後 5 個交易日與較舊行情標示。無效列不視為已完成，單日寫入失敗完整回滾。詳見 [階段四交付](docs/plan/08stock_tool_stage4_delivery.md)。

歷史股利採每檔整段查詢，例如同一股票 2024/06、2024/09、2025/06 有缺漏，只發一個涵蓋最早至最晚缺漏日的 FinMind 請求，仍保留前後 31 日查詢重疊與實際除權息日核對。每分鐘 4 次限制不變；1,000 檔光節流約 4 小時 10 分鐘，非 40 分鐘。進度顯示股利查詢第幾檔／總檔數。

下載行情成功不代表股利完整。掃描必須有涵蓋戰法回看期的股利核對紀錄，否則標示「還原資料未完整」並不產生正常命中。既有股利列會重用，但不直接當作完整性證明；升級後請自行執行一次「補齊歷史股利」。這個完整性檢查只套用全市場掃描，觀察清單及回測流程不變。

## 階段四 C：回測成本與 0050 基準

既有資料庫套用 `mysql/init/011_backtest_costs.sql` 後重建 backend；migration 可重複執行，新增回測任務的成本／基準快照，不改舊結果、不啟動任務。

| 設定 | 預設 | 說明 |
|---|---|---|
| `TRADE_FEE_RATE` | `0.001425` | 買、賣各一次手續費比例 |
| `TRADE_FEE_DISCOUNT` | `1.0` | 折扣，0 < 值 ≤ 1；六折填 0.6 |
| `TRADE_TAX_RATE_STOCK` | `0.003` | 普通股賣出稅率 |
| `TRADE_TAX_RATE_ETF` | `0.001` | ETF 賣出稅率 |

淨報酬 = 賣價 × (1 − 手續費 × 折扣 − 稅率) ÷ [買價 × (1 + 手續費 × 折扣)] − 1。報酬與勝率等統計以淨值為主，毛值並列；未平倉淨值假設估值日賣出。未模擬最低手續費 20 元、滑價及當沖減半稅率。查無種類以普通股計算並顯示警告。

0050 按交易相同買進日／賣出日開盤計算不扣成本的還原報酬；另顯示實際回測期間首日開盤到末日收盤的買進持有報酬。0050 不必在觀察清單，整批只準備一次，沿用 DB 優先、缺漏補同步；缺指定日期行情時回傳無資料與原因，不使用替代日期或 0%。超額報酬 = 策略淨報酬 − 0050 毛報酬。

舊結果標示「需重新回測」，不納入淨績效彙總；需自行按回測產生新結果。成本在接受任務時保存，結果使用當次快照，不隨後續設定變更。明細顯示其所屬結果的快照。

## 階段四 B：候選訊號績效追蹤

既有資料庫依序套用 009～011 後，套用 `mysql/init/012_signal_tracking.sql` 並重建 backend。012 可重複執行，保留首次部署日期與既有資料，不更動排程。`SIGNAL_TRACKING_HORIZONS` 預設 `1,5,10,20`，接受逗號分隔的 1～60 正整數；修改只影響之後新增的訊號。

全市場掃描所有戰法只列入進場事件：今天符合且前一個有效交易日不符合。候選、訊號歷史與績效追蹤都使用此口徑；觀察清單與回測維持原判定。連續符合只計入延續中，不列入候選或新增歷史；前日資料不足列為歷史不足，不能當作進場。最低成交金額僅用於頁面查詢篩選，不影響掃描判定。

每次掃描發佈時，正常進場命中會保存為歷史。同日同股票同戰法重跑保留首次價格、指標與成本快照，只更新最後出現時間；不同日期分開記錄。訊號自部署日開始累積，不由舊候選倒填。

在「全市場掃描」的「戰法績效追蹤」查看戰法 × 觀察期彙總，可篩選日期、種類、成交金額及排除較舊行情。點戰法展開訊號明細，每頁 50 筆。少於 30 個完成樣本標示「樣本不足」；無資料顯示無資料，並非 0%。

進場採訊號後下一有效交易日開盤，觀察期 1 使用進場隔一個交易日收盤；觀察期 N 使用進場日之後第 N 個市場交易日收盤。每次掃描發佈後只讀 DB 回填，尚未到期保持待計算，缺少日曆／0050 等資料顯示原因；已完成結果不重算。淨報酬使用訊號建立時的成本，0050 為毛報酬。不同進場事件仍可能有重疊持有期間，不能當作互相獨立的交易樣本。舊訊號歷史保留，由使用者另行清理；程式不刪除或重算舊訊號。

歷史初始化會寫入大量行情，建議先完成行情與股利初始化，再執行回測，避免兩者競爭相同行情資料列。完整驗證結果與尚待完成的外部資料項目見 [階段四交付](docs/plan/08stock_tool_stage4_delivery.md)。


## 分割與減資還原

既有 DB 套用 [013_price_events.sql](mysql/init/013_price_events.sql) 後重建 backend，再執行「補齊分割／減資」。Migration 可重複執行，只新增價格事件表及每日同步紀錄表。完成補齊後請重新回測，舊結果會標記過期；0050 事件變動會讓所有保存其基準的舊結果過期。

`POST /market-scan/initialize` 支援三種 mode：prices 只下載行情；dividends 補股利及價格事件；price_events 只補價格事件並重算受影響標的全部還原價。後兩種都不下載行情；股利範圍沿用 required_days，價格事件固定查 2011-01-01 至台北當天。

分割、反分割與面額變更使用 FinMind TaiwanStockSplitPrice，不帶 data_id；上市減資使用 TWSE TWTAUU，上櫃減資使用 TPEx revivt。三者均全市場查詢 2011-01-01 至台北當天。18:00 觀察清單排程、手動回測及全市場掃描／事件初始化共用一次同步入口。正常成功情況下，價格事件的 FinMind 每天最多 1 次，與股票檔數無關；當天已完成同步便跳過全部來源。三來源任一失敗或寫入失敗，complete=false，本次不重試，但下次任務允許重試，因此失敗日不是嚴格每日上限。這個次數不包含行情與股利請求。

同步前會確保 0050 基準主檔存在，其他事件只寫入 stocks 已存在的代號；逐檔行情同步及回測 prepare_data 只讀 DB 價格事件。回測沒有排程，只在使用者手動執行時同步。19:00 全市場掃描仍受原有啟用設定控制。

價格事件係數為來源 reference_price ÷ before_close，套用事件日以前的 OHLC；不調整成交量。股利公式維持原狀，同日股利與價格事件兩個係數都套用。來源失敗記入回測 errors、觀察清單錯誤紀錄或掃描 warnings，不暴露 token；全市場任一價格事件來源失敗，該次不新增股利完整性紀錄。既有完整性紀錄不代表已完成這次價格事件補齊，升級後仍須手動補齊。
